The stable and main spec-driven core layout matched at retrieval:

```text
openspec/
├── config.yaml
├── specs/<capability-path>/spec.md
└── changes/<change-id>/
    ├── .openspec.yaml
    ├── proposal.md
    ├── design.md
    ├── tasks.md
    └── specs/<capability-path>/spec.md
```

Current capability specs describe existing behavior. Change-local specs use `ADDED`, `MODIFIED`, and `REMOVED` requirement sections; Groundwork currently projects proposed records as `ADDED` requirements because its change record does not claim modification/removal semantics. Verified delivery records remain evidence and are not projected as intent.

Assumptions:

- Groundwork `spec.json` remains canonical; the OpenSpec tree is derived and replaceable.
- Export is explicit and never invokes `openspec init`, installs OpenSpec, or depends on its runtime.
- Groundwork current records map to the current capability spec. Proposed records map to the change proposal and delta spec. Verified delivery evidence is not promoted into either intended surface. Architecture, contracts, ordered information flow, and cross-Spec dependencies map to `design.md`; the compiled task graph maps to `tasks.md`.
- A future OpenSpec layout or delta-semantics change requires a new dated record, fixture update, and exporter-version decision.
